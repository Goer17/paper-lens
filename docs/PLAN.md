# PaperLens — Product Plan

**Status:** v0.1 shipped, iterating
**Product name:** PaperLens
**Repository:** paper_reader (workspace)
**Last updated:** 2026-10-20

---

## 1. Vision

PaperLens is a local-first AI reading desk for research papers. It should make the path from
"open a PDF" to "understand a specific claim, with evidence" as short as possible.

The product combines three things that are usually separate:

1. a calm, fast PDF reader;
2. Zotero-like annotations and margin notes;
3. an AI assistant that can see the paper and the user's annotations, and that cites its evidence.

The AI is not the product. Reading is the product; the AI is a lens on the reading.

## 2. Problem

Researchers, students and engineers read dense PDFs and need to:

- keep a library of papers organized without a heavy reference manager;
- mark claims, definitions and figures while reading;
- ask questions about a paper without copying text into a separate chat tool;
- verify that an AI answer is actually supported by the paper.

Existing tools either focus on reference management, on PDF markup, or on chat. PaperLens connects
them while keeping data local and the interface small.

## 3. Target users

- A researcher who reads several papers a week and wants a personal, searchable library.
- A student who needs explanations grounded in a specific paper.
- An engineer evaluating methods and collecting evidence across papers.
- A privacy-conscious user who wants to bring their own model provider.

## 4. Product principles

- **Local-first by default.** Library, annotations and chats live on the user's machine.
- **Evidence over generation.** Annotations are first-class AI context. Answers use explicit labels.
- **Fast reading, calm UI.** Monospace, compact, low-chrome; keyboard-friendly where practical.
- **Bring your own model.** Any OpenAI-compatible provider; automatic fallback; no lock-in.
- **Maintainable by agents and humans.** Small modules, explicit contracts, documentation and tests.
- **No hidden side effects.** Destructive actions are explicit; annotation deletion is deliberately
  instant as requested, while other destructive actions use centered confirmations.

## 5. Scope

### 5.1 Workspace and access — shipped

- Random access token generated by the server, stored in `server/data/token.txt`, printed on boot.
- Token login once; browser remembers it in `localStorage`.
- `?token=` shortcut for first-time or automated access.
- Sign out on the current browser.
- Single-user, loopback-only API by default.

### 5.2 Library and folders — shipped

- Collapsible left sidebar with a **tree of folders**:
  - create root and nested folders;
  - expand/collapse;
  - rename via centered prompt;
  - drag folders onto other folders to re-parent (cycles rejected);
  - drag folders onto All Papers to move them to the root;
  - delete a folder: direct subfolders move up one level, papers become Uncategorized.
- Upload PDFs by button, drag-and-drop onto a folder, or drop onto the empty reader.
- Multi-file upload (up to 20 files, 100 MB each).
- Drag papers between folders.
- Search by title/filename; annotation counts per paper and folder.
- Paper titles:
  - an LLM detects the real title on upload from first-page text;
  - fallback to PDF metadata or filename;
  - titles are editable from the sidebar (double-click or pencil).

### 5.3 PDF reader — shipped

- PDF.js rendering with lazy page rendering (first pages eagerly, the rest on approach).
- Fit-width layout that reflows when the sidebar, notes rail or AI panel opens.
- Zoom controls, page number input, previous/next page.
- PDF.js text layer for native selection and copy/paste.
- Page numbers and reading-position tracking.

### 5.4 Annotations and notes — shipped

- **Highlight** and **underline** via native browser text selection:
  - Select mode: select text → floating menu (colour swatches + Highlight/Underline);
  - Highlight/Underline mode: selecting text applies the annotation immediately, then returns to
    Select;
  - only Box mode uses a drag rectangle.
- **Box** annotations capture the enclosed text and a PNG crop of the page region.
- Annotation colours: yellow, green, blue, pink; recolour from the selection toolbar.
- Hover an annotation for 0.5 s to show `@page:label` in a tooltip at the cursor's bottom-right.
  Clicking elsewhere clears the blue selection ring. No persistent labels.
- **Notes rail** on the right of the page:
  - double-click an annotation opens a rounded sticker;
  - sticker width matches the rail and is vertically aligned with the annotation;
  - overlapping stickers are pushed down;
  - notes autosave and persist.
- Delete an annotation instantly from its toolbar (no confirmation).
- Annotation labels are stable per paper/type (`highlight_1`, `underline_2`, `box_1`).

### 5.5 AI assistant — shipped

- Slide-over chat locked to the active paper.
- Attach annotations by dragging them into the panel; composer shows chips like `@3:underline_1`.
- Box citations include text and a crop; vision-capable models receive the image.
- Streaming SSE responses; stop button; clear thread; persisted history.
- Visible tool-call trace including arguments and success/failure.
- Tools:
  - `search_paper`, `read_page`, `read_pages`, `list_annotations`, `read_annotation`,
    `get_paper_info`;
  - `list_skills`, `use_skill`, `read_skill_file` when skills are installed.
- Answers are Markdown with GFM tables/code and KaTeX math.
- Inline citation labels become links that jump to and flash the annotation.
- Short model narration before tool calls is suppressed; long preambles stream normally.

### 5.6 Models and language — shipped

- Provider list stored locally:
  - base URL, API key, model name, display name, optional vision flag;
  - add, reorder (priority), enable/disable, test connection, delete;
  - disabling moves the model to the bottom and excludes it from calls;
  - keys never returned unmasked.
- Automatic fallback to the next enabled model on failure before visible output/tool success.
- Response language preference: English, Chinese, Japanese, Korean, Spanish, French, German.
- Seed the debug model from `DEEPSEEK_API_KEY` on a fresh database.

### 5.7 Skills — shipped

- Upload a `.zip` skill package; extracted server-side with path-traversal and size protections.
- `SKILL.md` frontmatter provides name/description; supporting files are browsable by the agent.
- Four-per-row folder grid with file count and delete.
- Agent can read instructions/files; uploaded code is never executed.

### 5.8 Settings and UI — shipped

- **Basic:** theme/accent colour presets plus a custom colour.
- **Models:** response language, fallback explanation, provider list, add-model form.
- **Skills:** upload/drop zip, skill cards, delete.
- Accent colour applies globally through CSS variables.
- Centered confirm/prompt dialogs (no browser `alert`/`confirm`/`prompt`), keyboard support,
  destructive actions focus Cancel.
- All UI copy in English; monospace design system.

## 6. Core flows

### First launch

1. User starts `npm run dev` and gets the token from `server/data/token.txt` (`npm run token`).
2. Enters the token once; browser stores it.
3. Empty workspace shows a drop zone and a default folder.

### Add a paper

1. User drops a PDF onto a folder (or uploads via button).
2. Server validates and stores the file, creates a provisional title.
3. The first enabled model reads the first-page text and returns the real title.
4. The paper appears in the folder with its detected title; user can rename it.

### Read and annotate

1. Open a paper; the reader fits pages to the available width.
2. Select text → choose Highlight/Underline (or use H/U mode).
3. Box a figure with the Box tool.
4. Double-click an annotation to add a note; the sticker aligns in the rail.
5. Hover an annotation to see its label; click away to clear the selection ring.

### Ask with evidence

1. Drag one or more annotations into the AI panel.
2. The composer shows `@page:label` chips.
3. Ask a question; the assistant searches/reads the paper and answers with citations.
4. Click a citation link to jump to the annotation.

### Configure a model

1. Settings → Models → New model.
2. Enter base URL, API key, model name (and vision if applicable).
3. Test, reorder, disable or delete.
4. Response language is set in the same tab.

### Install a skill

1. Settings → Skills → upload zip.
2. PaperLens extracts it and reads `SKILL.md`.
3. In chat, the agent can call `use_skill` when the task matches the skill description.

## 8. Non-functional requirements

- **Local-first:** no telemetry, analytics or cloud sync.
- **Security:** token-protected API; loopback binding; API keys masked; safe skill extraction; no
  uploaded code execution.
- **Performance:** PDF pages lazy-render; server caches extracted text; chat streams.
- **Resilience:** failed model calls fall back; failed title detection keeps filename; uploads are
  validated before storage.
- **Maintainability:** strict TypeScript, separated packages, documented API/SSE contracts, smoke
  test, TODO and dev log.
- **Accessibility:** keyboard dialogs, focus states, readable contrast; further audit planned.
- **Portability:** Node 22+, no native modules; SQLite via `node:sqlite`.

## 9. Technical direction

- **Frontend:** React 19 + Vite, PDF.js for rendering, react-markdown/KaTeX for answers, no UI
  component library.
- **Backend:** Express 4 + TypeScript (ESM), SSE for chat, OpenAI SDK for providers.
- **Storage:** SQLite (`node:sqlite`) + local files; additive migrations.
- **AI context:** server snapshots annotations; tools search cached page text; page text extracted by
  `unpdf`.
- **Title detection:** first-page text + metadata + filename → first enabled model → fallback.
- **Skills:** adm-zip extraction with path/size checks; instructions are read, never executed.
- **Deployment:** local dev (Vite + API), single-port production (API serves the built SPA), and a
  loopback-only Docker Compose image (see [DEPLOYMENT.md](DEPLOYMENT.md)). `deploy` is the working
  branch; `main` only receives user-approved merges.

## 11. Milestones

### v0.1 — Reading desk (shipped)

- Token workspace, local SQLite library, nested folders, upload/search.
- PDF reader, native selection annotations, boxes, notes rail.
- SSE AI chat with citations, tools, fallback, language, KaTeX.
- Skills, themes, centered dialogs.
- LLM title detection and editable paper titles.

### v0.2 — Reading depth

- Cross-page text selections.
- Remember last page/zoom; PDF outline.
- Annotation export (Markdown/JSON) and bulk actions.
- Backfill titles for existing papers.
- Folder sorting and keyboard tree navigation.

### v1.0 — Reliable research workspace

- Automated test suite and CI.
- OCR fallback for scanned PDFs.
- Library metadata (authors, year, venue, tags).
- Import from DOI/arXiv/Zotero.
- Optional multi-thread chat per paper and usage accounting.

## 12. Success criteria

- A new user can add a paper, highlight a claim, pin a note, and get a cited answer in under two
  minutes without reading documentation.
- Every AI answer about paper content can be traced to a page snippet or annotation.
- The workspace survives restarts with all annotations, notes, chats and settings intact.
- No user library data leaves the machine unless sent to a user-configured provider.
- A new contributor can run typecheck, build and smoke tests from `AGENTS.md` alone.

## 13. Out of scope (for now)

- Multi-user accounts, team sharing, cloud sync.
- Mobile apps.
- OCR for scanned PDFs (planned later).
- Running arbitrary skill code/server-side scripts.
- Citation/reference management with BibTeX ingestion (candidate for v1).
- PDF editing or form filling.

## 14. Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| LLM hallucination | Server-snapshotted citations, tools, explicit citation labels, page grounding |
| Provider outage/rate limits | Ordered fallback chain and clear warnings |
| Large PDF rendering stalls | Lazy pages, cached text extraction, fit-width layout |
| Skill zip attacks | Path checks, uncompressed-size limits, no execution |
| Data loss | Local SQLite + files; docs warn to back up `server/data`; no automatic resets |
| Title detection latency | 20 s timeout, parallel calls, filename/metadata fallback |
| Secret leakage | Masked model responses, no token logging, loopback binding |
